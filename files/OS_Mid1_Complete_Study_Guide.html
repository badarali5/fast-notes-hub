Chapter 1

Introduction to Operating Systems

1.1 — What is an Operating System?

Imagine you bought a powerful gaming PC. The hardware — CPU, RAM, GPU — is just metal and silicon. Without software to manage it all, you'd have a very expensive paperweight. That's exactly where the Operating System (OS) comes in.

Definition

An Operating System is a program that acts as an intermediary (middleman) between a user and the computer hardware. It manages hardware resources and provides services for application programs.

Think of it like a restaurant:

  • You (User) = customer who wants food (services)
  • Waiter (OS) = takes your order, coordinates with kitchen
  • Kitchen + Ingredients (Hardware) = actual processing happens here
  • Menu Items (Applications) = Word, Chrome, games, etc.

OS Goals:

  • Execute user programs and make solving problems easier
  • Make the computer system convenient to use
  • Use hardware in an efficient manner

Computer System Structure (4 components):

  • Hardware — CPU, memory, I/O devices (the physical stuff)
  • Operating System — controls and coordinates hardware
  • Application Programs — Word processor, browsers, games
  • Users — people, machines, other computers
Key Term

The Kernel is "the one program running at all times on the computer." It is the core of the OS. Everything else is either a system program or an application program.

⚡ Exam Point

The OS acts as a resource allocator (decides who gets CPU time, memory, etc.) AND a control program (manages execution to prevent errors and misuse). Remember both roles!

1.2 — Computer-System Organization

Modern computers have one or more CPUs and multiple device controllers (for disk, keyboard, display, etc.) all connected via a common bus that shares memory.

How I/O Works — The Basic Flow

  1. The CPU tells a device controller to perform an I/O operation (e.g., read from disk)
  2. The device controller uses its local buffer to temporarily hold data
  3. CPU moves data from main memory to/from those local buffers
  4. When the controller is done, it interrupts the CPU to say "I'm finished!"
Definition

A Device Driver is a software module for each device controller. It provides a uniform interface between the controller and the kernel — think of it as a translator.

Interrupts — The OS's Notification System

An interrupt is a signal that tells the CPU "stop what you're doing, something needs your attention!" It's like a phone ringing while you're working — you pause, answer the call, then return to work.

TypeWhat Is It?Example
Hardware InterruptTriggered by a hardware deviceKeyboard press, disk done reading
Software Interrupt (Trap/Exception)Triggered by software eventDivision by zero, system call

How Interrupts Work (Step by Step):

  1. Interrupt occurs (hardware or software)
  2. CPU saves its current state (registers + program counter)
  3. CPU looks up the Interrupt Vector (a table of addresses for each interrupt handler)
  4. CPU jumps to the appropriate Interrupt Service Routine (ISR)
  5. ISR handles the interrupt
  6. CPU restores saved state and continues previous work
💡 Simple Analogy

A Trap = you accidentally call 911 (software-generated, caused by error or request). A Hardware Interrupt = someone physically calls 911 (external event). Both reach the dispatch center (ISR) but via different channels.

1.2 (cont.) — Storage Structure & Hierarchy

Not all storage is equal. There's a hierarchy from fast-but-expensive to slow-but-cheap:

LevelStorage TypeSpeedSizeVolatile?
1RegistersFastestBytesYes
2Cache (L1, L2, L3)Very FastKB–MBYes
3Main Memory (RAM)FastGBYes
4SSD / NVMMediumGB–TBNo
5Hard Disk (HDD)SlowTBNo
6Optical / TapeSlowestTB+No
Key Concepts

Volatile = data is lost when power is off (RAM, registers, cache). Non-volatile = data persists without power (HDD, SSD).

Caching = copying data from a slower storage to a faster one temporarily. Main memory acts as a cache for the hard disk.

DMA (Direct Memory Access): For fast I/O devices, instead of the CPU handling every byte individually, DMA transfers entire blocks of data directly between the device and main memory, generating only one interrupt per block (not per byte). This frees the CPU for other work.

1.3 — Computer-System Architecture

Types of Systems

  • Single-Processor Systems — One general-purpose CPU. Most common historically.
  • Multiprocessor Systems (Parallel Systems) — Multiple CPUs working together. 3 main advantages:
    • Increased throughput (more work done)
    • Economy of scale (share resources)
    • Increased reliability (if one fails, others keep running)
TypeHow it WorksExample
Asymmetric Multiprocessing (AMP)Each processor assigned a specific task. One "boss" processor controls others.Old embedded systems
Symmetric Multiprocessing (SMP)All processors are equal — each can run any task. Peer-to-peer relationship.Modern PCs, servers
⚡ Exam Point

Multicore = multiple CPU cores on ONE chip. Multiprocessor = multiple physical chips. Both enable parallel processing but multicore cores share on-chip cache, making communication faster.

Clustered Systems

Multiple complete computer systems (nodes) working together, usually sharing storage via a Storage Area Network (SAN). Provides high availability — if one machine fails, others take over.

1.4 — Operating-System Operations

Bootstrap Program

When you turn on your computer, the very first program that runs is the bootstrap program (also called firmware/BIOS/UEFI). It:

  1. Initializes all hardware components
  2. Locates the OS kernel on disk
  3. Loads the kernel into memory
  4. Starts execution of the kernel

Multiprogramming vs. Multitasking

ConceptWhat It MeansAnalogy
MultiprogrammingMultiple programs kept in memory simultaneously. When one waits for I/O, CPU switches to another. Maximizes CPU utilization.A chef juggling multiple dishes — when one is in the oven, work on another.
Multitasking (Timesharing)CPU switches between programs so fast that each user perceives their own dedicated machine. Response time < 1 second.A very fast chef who appears to be at every table simultaneously.

Dual-Mode Operation — THE MOST IMPORTANT CONCEPT

How does the OS protect itself from badly-written programs? Through dual-mode operation:

Dual Mode

User Mode: Applications run here. Limited privileges. Cannot directly access hardware.
Kernel Mode (also called supervisor/system/privileged mode): OS runs here. Full access to all hardware and instructions.

A hardware mode bit (0 = kernel, 1 = user) indicates the current mode.

How switching happens:

  1. Application makes a system call
  2. Hardware switches mode bit to kernel mode
  3. OS executes the privileged operation
  4. OS returns result and switches back to user mode
⚡ Exam Point

Privileged instructions can ONLY execute in kernel mode (e.g., accessing I/O directly, modifying memory protection). If a user program tries to execute a privileged instruction, it causes a trap → the OS handles it (usually by killing the program).

Timer

To prevent one program from hogging the CPU forever (infinite loops!), the OS sets a timer that generates an interrupt after a certain time period. The counter decrements with each clock tick; when it hits zero → interrupt → OS regains control.

1.5 — Resource Management

The OS manages all resources. Here's a quick overview of each:

ResourceWhat OS Does
Process ManagementCreate/delete processes, scheduling, synchronization, communication, deadlock handling
Memory ManagementTrack which memory is used by whom, allocate/deallocate, decide what stays in memory
File-System ManagementCreate/delete files & directories, map files to storage, backup, access control
Mass-Storage ManagementDisk scheduling, free-space management, mounting/unmounting, partitioning
Cache ManagementDecide what data to cache, how long, replacement policies
I/O SubsystemBuffering, caching, spooling, device drivers
I/O Subsystem Terms

Buffering = storing data temporarily while it is being transferred (e.g., download buffer).
Caching = storing parts of data in faster storage for performance (e.g., browser cache).
Spooling = overlapping output of one job with input of others (e.g., printer spooler — jobs queue up).

2.1 — Operating-System Services

The OS provides services that make life easier for both users and programmers. Think of it as a government — provides services (police, roads, postal system) so individual citizens don't have to build their own.

Services for Users

  • User Interface (UI) — CLI (command line), GUI (graphical), touch-screen
  • Program Execution — Load program into memory and run it
  • I/O Operations — Handle all I/O since users can't access hardware directly
  • File-System Manipulation — Read, write, create, delete files and directories
  • Communications — Between processes (same machine or network), via shared memory or message passing
  • Error Detection — Detect and handle hardware/software errors

Services for Efficient System Operation

  • Resource Allocation — When multiple processes run, distribute CPU time, memory, I/O fairly
  • Logging — Track which users use what resources (accounting)
  • Protection & Security — Control access to resources, authenticate users, defend against attacks

2.3 — System Calls

This is one of the MOST important topics in the entire course.

Definition

A System Call is the programming interface through which application programs request services from the OS. It's the formal "doorbell" a program rings to ask the kernel to do something privileged on its behalf.

Think of it like ordering from a restaurant menu. You (user program) can't walk into the kitchen (kernel) yourself — you use the menu (API) to request specific dishes (services) from the waiter (system call interface).

System Calls vs. API

Programmers rarely use system calls directly. They use a higher-level API (Application Programming Interface) that internally calls the appropriate system call.

  • Windows → Win32 API
  • POSIX (Linux/macOS/Unix) → POSIX API
  • Java → Java API (goes through JVM)
// You write this (API call):
printf("Hello World\n");

// Internally, printf() calls the write() system call:
write(1, "Hello World\n", 12);

// write() triggers a software interrupt to switch to kernel mode
// The kernel performs the actual I/O to your screen
// Then returns to user mode

Passing Parameters to System Calls

Three methods exist to pass information to the OS:

  1. Registers — Pass parameters directly in CPU registers (simplest, but limited)
  2. Memory Block/Table — Store parameters in memory, pass address in a register (used by Linux & Solaris)
  3. Stack — Program pushes parameters onto stack; OS pops them

Types of System Calls (6 Categories)

CategoryExamples
Process Controlcreate/terminate process, load/execute, wait, allocate memory — fork(), exit(), wait()
File Managementcreate/delete file, open, close, read, write — open(), read(), write(), close()
Device Managementrequest/release device, read/write device — ioctl()
Information Maintenanceget/set time, get system data, process attributes — getpid(), alarm()
Communicationscreate/delete connection, send/receive messages, shared memory — pipe(), shmget()

2.8 — Operating-System Structure

How should we organize the millions of lines of OS code? Several architectural approaches exist:

1. Monolithic (Simple/Traditional) — Original UNIX

Everything is in one large kernel. All OS services run in kernel space. Fast because no inter-component communication overhead, but hard to maintain and debug.

2. Layered Approach

OS divided into N layers. Layer 0 = hardware. Layer N = user interface. Each layer uses services ONLY from the layer below it. Like an onion — each layer wraps around the one inside it. Clean but can be slow due to overhead of passing through many layers.

3. Microkernel — Mach

Move as much functionality OUT of the kernel and into user space. Kernel only does essential functions (basic scheduling, IPC, memory management). Everything else (file system, device drivers) runs as user-space processes.

BenefitCost
MicrokernelEasier to extend, more reliable, more securePerformance overhead (user↔kernel communication)
MonolithicFast (no IPC needed between components)One bug can crash entire OS

4. Modules (LKMs — Loadable Kernel Modules)

Modern approach. Core kernel is minimal. Additional features can be loaded/unloaded at runtime as modules. Linux uses this — you can insmod a driver when you plug in a new device, rmmod when you're done.

5. Hybrid Systems

Most real OSes combine approaches. Linux = monolithic + modular. macOS = microkernel (Mach) + BSD Unix parts + dynamically loadable modules. Windows = mostly monolithic + microkernel personality subsystems.

2.9 — Building and Booting an OS

Boot sequence (what happens when you press the power button):

  1. Power on → CPU starts at a fixed memory address
  2. BIOS/UEFI (firmware in ROM/EEPROM) runs — performs hardware tests (POST)
  3. BIOS locates the boot block (bootloader) on disk
  4. Bootloader (e.g., GRUB) loads the OS kernel into RAM
  5. Kernel initializes hardware, starts system daemons
  6. System is ready to use
💡 Terminology

GRUB = Grand Unified Bootloader — most common Linux bootloader. Lets you choose between multiple kernels/OSes.
UEFI = Unified Extensible Firmware Interface — modern replacement for BIOS. Supports larger disks, faster boot, Secure Boot.

2.10 — OS Debugging

Chapter 3

Processes

3.1 — Process Concept

Definition

A Process is a program in execution. A program is a passive entity stored on disk (like a recipe). A process is an active entity — it's when you actually start cooking. One program (recipe) can become multiple processes (multiple chefs cooking simultaneously).

What Does a Process Look Like in Memory?

A process in memory is divided into these sections (from top address to bottom):

SectionWhat's StoredGrows Direction
StackTemporary data — function parameters, return addresses, local variablesDownward ↓
HeapMemory dynamically allocated at runtime (malloc, new)Upward ↑
Data SectionGlobal and static variablesFixed
Text SectionThe actual program code (machine instructions)Fixed (bottom)
// Example showing which section each variable goes to:
#include <stdio.h>
#include <stdlib.h>

int global_var = 10;  // DATA SECTION (global variable)

int main() {
    int local_var = 5;           // STACK (local variable)
    int *heap_var = malloc(100); // HEAP (dynamically allocated)
    
    // The code itself is in the TEXT section
    free(heap_var);
    return 0;
}

3.1 (cont.) — Process States

As a process runs, it changes state. There are 5 states:

StateMeaning
NewProcess is being created
ReadyProcess is waiting to be assigned to a CPU (it's ready to run but CPU is busy)
RunningInstructions are being executed on the CPU
WaitingProcess is waiting for some event (e.g., I/O completion, signal)
TerminatedProcess has finished execution

Process State Transition Diagram

⚡ Exam Point

Only ONE process can be in the RUNNING state per CPU core. Many processes can be READY or WAITING simultaneously. The transition from Ready→Running is called dispatch. Running→Waiting happens when a process needs I/O.

3.1 (cont.) — Process Control Block (PCB)

Definition

The PCB (Process Control Block), also called task control block, is a data structure the OS maintains for each process. It's like the process's "ID card" + "medical record" — everything the OS needs to know about that process.

PCB contains:

  • Process State — new, ready, running, waiting, terminated
  • Process Number (PID) — unique identifier for this process
  • Program Counter (PC) — address of the NEXT instruction to execute
  • CPU Registers — all register contents (saved when process is paused)
  • CPU Scheduling Info — priority, queue pointers
  • Memory Management Info — memory limits, page tables
  • Accounting Info — CPU time used, time since start
  • I/O Status Info — open files, allocated devices

In Linux, the PCB is implemented as the C structure task_struct.

3.2 — Process Scheduling

Definition

The Process Scheduler selects which process from the ready queue gets to run next on the CPU. Goal: maximize CPU utilization — keep the CPU busy as much as possible.

Scheduling Queues

  • Ready Queue — All processes in main memory, ready and waiting to execute. Implemented as a linked list of PCBs.
  • Wait Queue — Processes waiting for an event (e.g., I/O completion). There's one wait queue per device.

Processes migrate between these queues throughout their lifetime. A process starts in the ready queue → gets CPU → may go to wait queue for I/O → returns to ready queue when I/O is done.

3.2 (cont.) — Context Switch

Definition

A Context Switch happens when the CPU switches from running one process to another. The OS must save the state of the old process (into its PCB) and load the state of the new process (from its PCB).

Step by step:

  1. Process P0 is running; an interrupt/system call occurs
  2. OS saves state of P0 into PCB₀ (registers, PC, etc.)
  3. OS loads state of P1 from PCB₁
  4. P1 starts running
  5. When P1 is interrupted, reverse the process to restore P0
⚠️ Key Fact

Context-switch time is pure overhead — no useful work is done during the switch. The more complex the OS and PCB, the longer the switch takes. Some hardware provides multiple register sets per CPU to speed this up.

3.3 — Process Creation (C Coding)

Processes can create other processes. The creator is the parent, the created one is the child. This forms a tree of processes. Each process has a unique PID (Process Identifier).

In Linux, the root of this tree is systemd (PID = 1).

Resource Sharing Options

  • Parent and children share all resources
  • Children share a subset of parent's resources
  • Parent and child share no resources

Execution Options

  • Parent and children execute concurrently
  • Parent waits until children terminate

UNIX System Calls: fork(), exec(), wait()

System CallWhat It DoesReturn Value
fork()Creates a new child process that is an exact duplicate of the parentReturns PID of child to parent, returns 0 to child, -1 on error
exec() / execlp()Replaces the current process's memory image with a new programDoesn't return on success (process is replaced!)
wait()Parent blocks until a child terminates. Gets child's exit status.PID of terminated child
exit()Terminates the calling process, sends status to parent(no return — process ends)
#include <sys/types.h>
#include <stdio.h>
#include <unistd.h>

int main() {
    pid_t pid;
    
    /* Fork a child process */
    pid = fork();
    
    if (pid < 0) {            /* Error: fork failed */
        fprintf(stderr, "Fork Failed\n");
        return 1;
    }
    else if (pid == 0) {       /* This is the CHILD process (pid = 0) */
        execlp("/bin/ls", "ls", NULL);
        /* execlp replaces child's memory with the 'ls' program */
        /* If execlp succeeds, this line is NEVER reached */
    }
    else {                     /* This is the PARENT process (pid = child's PID) */
        wait(NULL);              /* Parent waits for child to finish */
        printf("Child Complete!\n");
    }
    
    return 0;
}
⚡ Exam: Dry Run of fork()

After fork(): TWO processes exist running the SAME code. The ONLY way to tell them apart is by the return value of fork().
• Parent gets: pid = <child's actual PID> (a positive number)
• Child gets: pid = 0
• Error: pid = -1

execlp() Details

execlp(path, arg0, arg1, ..., NULL)

  • Searches for the program in the PATH environment variable
  • First argument = filename of executable
  • Subsequent arguments = command-line arguments to new program
  • Must end with NULL
  • If successful, it does NOT return — the calling process is completely replaced
  • If it fails, it returns -1 and sets errno

3.3 (cont.) — Process Termination

A process terminates when it:

  • Executes its last statement and calls exit()
  • Is killed by its parent via abort()

When a process exits, its resources are deallocated by the OS.

TermDefinition
Cascading TerminationWhen a parent exits, all children (and grandchildren) are also terminated. Initiated by the OS.
Zombie ProcessA child that has terminated but whose parent has NOT yet called wait(). It still has an entry in the process table (parent needs to read exit status).
Orphan ProcessA child whose parent has terminated WITHOUT calling wait(). In Unix, orphans are adopted by init/systemd (PID 1).

3.4 — Interprocess Communication (IPC)

Processes can be independent (don't share data) or cooperating (share data and communicate). Cooperating processes need IPC.

Why Cooperating Processes?

  • Information sharing — multiple users need same data
  • Computation speedup — parallelize tasks
  • Modularity — divide system into separate modules
  • Convenience — multiple tasks at once

Two Models of IPC

AspectShared MemoryMessage Passing
MechanismProcesses share a region of memory; read/write directlyProcesses send/receive messages via OS-managed channel
SpeedFast (no kernel involvement after setup)Slower (every message involves a system call)
SynchronizationExplicit (semaphores/mutexes needed)Built-in (send/receive operations)
Address SpaceShared — same memory regionSeparate — no shared memory
Best ForSame machine, large data transfersDistributed systems, structured messages

Producer-Consumer Problem (Classic Example of IPC)

A producer process generates data; a consumer process uses it. They share a buffer.

  • Unbounded buffer — no limit on buffer size → producer never waits, consumer waits only when buffer is empty
  • Bounded buffer — fixed size → producer waits when buffer full, consumer waits when buffer empty
/* Shared variables (in shared memory) */
#define BUFFER_SIZE 10

typedef struct { /* ... item data ... */ } item;

item buffer[BUFFER_SIZE];
int in = 0;   /* next free position (producer writes here) */
int out = 0;  /* first full position (consumer reads here) */

/* Buffer is EMPTY when: in == out */
/* Buffer is FULL when:  ((in + 1) % BUFFER_SIZE) == out */

/* PRODUCER CODE */
void producer() {
    item next_produced;
    while (true) {
        /* produce an item */
        while (((in + 1) % BUFFER_SIZE) == out)
            ; /* do nothing — buffer FULL, wait */
        buffer[in] = next_produced;
        in = (in + 1) % BUFFER_SIZE;
    }
}

/* CONSUMER CODE */
void consumer() {
    item next_consumed;
    while (true) {
        while (in == out)
            ; /* do nothing — buffer EMPTY, wait */
        next_consumed = buffer[out];
        out = (out + 1) % BUFFER_SIZE;
        /* consume the item */
    }
}
⚠️ Shortcoming

This basic implementation can only use BUFFER_SIZE - 1 slots (not all 10). It also doesn't handle synchronization — if both producer and consumer run simultaneously, race conditions can corrupt data. This is fixed with semaphores (Chapter 6).

POSIX Shared Memory (3.5 — C Coding)

POSIX provides system calls to create and manage shared memory segments:

/* ====== PRODUCER (Writer) ====== */
#include <sys/shm.h>
#include <sys/mman.h>

const int SIZE = 4096;
const char *name = "OS";

/* Step 1: Create/open shared memory object */
int fd = shm_open(name, O_CREAT | O_RDWR, 0666);

/* Step 2: Set its size */
ftruncate(fd, SIZE);

/* Step 3: Memory-map it into our address space */
char *ptr = (char*)mmap(0, SIZE, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);

/* Step 4: Write to shared memory */
sprintf(ptr, "Hello");


/* ====== CONSUMER (Reader) ====== */
int fd = shm_open(name, O_RDONLY, 0666);  // Open existing
char *ptr = (char*)mmap(0, SIZE, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);
printf("%s", (char*)ptr);  // Read from shared memory
shm_unlink(name);           // Remove shared memory object

3.7.1 & 3.7.4 — Pipes (C Coding)

Definition

A pipe is a conduit allowing two processes to communicate. Think of it as an actual pipe — data flows in one end and out the other. They are unidirectional (one-way) communication channels.

Ordinary Pipes (Anonymous Pipes)

  • Created with pipe(int fd[2])
  • fd[0] = read end, fd[1] = write end
  • Require a parent-child relationship (created before fork)
  • Exist only while processes are running
  • Unidirectional (need 2 pipes for bidirectional)
  • Windows calls these anonymous pipes
#include <stdio.h>
#include <string.h>
#include <unistd.h>

#define BUFFER_SIZE 25
#define READ_END    0
#define WRITE_END   1

int main() {
    char write_msg[BUFFER_SIZE] = "Greetings";
    char read_msg[BUFFER_SIZE];
    int fd[2];
    pid_t pid;
    
    /* Create the pipe */
    if (pipe(fd) == -1) {
        fprintf(stderr, "Pipe failed");
        return 1;
    }
    
    pid = fork();  /* Fork AFTER pipe creation so child inherits it */
    
    if (pid > 0) {    /* PARENT: writes to pipe */
        close(fd[READ_END]);   /* Close unused read end */
        write(fd[WRITE_END], write_msg, strlen(write_msg) + 1);
        close(fd[WRITE_END]);  /* Done writing */
    }
    else {            /* CHILD: reads from pipe */
        close(fd[WRITE_END]);  /* Close unused write end */
        read(fd[READ_END], read_msg, BUFFER_SIZE);
        printf("read: %s\n", read_msg);
        close(fd[READ_END]);   /* Done reading */
    }
    return 0;
}

Named Pipes (FIFOs) — 3.7.4

FeatureOrdinary PipesNamed Pipes (FIFOs)
Creationpipe(int fd[2])mkfifo()
Process RelationshipRequires parent-childNo relationship needed
PersistenceExists only while processes runExists in filesystem until deleted
AccessVia file descriptorsVia file path (like a regular file)
Multiple WritersNoYes

Named Pipes provide synchronization automatically — reading blocks if pipe is empty, writing blocks if pipe is full.

3.8.2 — Sockets (Basic Theory)

A socket is an endpoint for communication. Identified by an IP address + port number. Used for communication between processes on different machines over a network. Pipes only work on the same machine; sockets work anywhere.

💡 Pipes vs Shared Memory vs Message Passing

Use Pipes when: Simple, unidirectional data flow. Parent-child or shell piping (ls | grep).
Use Shared Memory when: High-speed, large data on same machine. Need bidirectional. (Requires synchronization!)
Use Message Passing when: Structured discrete messages. Different machines. Need built-in synchronization.

Chapter 5

CPU Scheduling — FIFO, SJF & SRTF

Basic Concepts

The CPU is the most valuable resource in a computer. We want to keep it busy 100% of the time. CPU Scheduling decides which process gets the CPU and for how long.

CPU-I/O Burst Cycle

Process execution alternates between CPU bursts (actually using the CPU) and I/O bursts (waiting for I/O). Short CPU bursts are very common; long ones are rare. The scheduler runs between CPU bursts.

When Does Scheduling Happen?

The CPU scheduler makes decisions when a process:

  1. Switches from running → waiting (e.g., I/O request)
  2. Switches from running → ready (e.g., interrupt)
  3. Switches from waiting → ready (e.g., I/O completion)
  4. Terminates
TypeWhen It AppliesCan Be Preempted?
Non-preemptiveOnly under conditions 1 & 4. Once CPU is given, process keeps it until it finishes or waits.No — process runs until done/waiting
PreemptiveUnder all 4 conditions. OS can forcibly take CPU from running process.Yes — OS can interrupt at any time

The Dispatcher

The Dispatcher is the module that gives control of the CPU to the process selected by the scheduler. It handles: context switching, switching to user mode, jumping to the correct location in the program. Dispatch latency = time for dispatcher to stop one and start another.

Scheduling Criteria — How Do We Judge?

CriterionDefinitionWe Want To...
CPU Utilization% of time CPU is busyMaximize ↑
ThroughputProcesses completed per time unitMaximize ↑
Turnaround TimeTotal time from submission to completionMinimize ↓
Waiting TimeTotal time spent in ready queueMinimize ↓
Response TimeTime from request submission to first responseMinimize ↓
Turnaround Time = Completion Time − Arrival Time
Waiting Time = Turnaround Time − Burst Time
Response Time = First CPU Time − Arrival Time

FCFS / FIFO — First-Come, First-Served

Algorithm

FCFS (FIFO): Processes are served in the order they arrive. The first one to request the CPU gets it first. Like a queue at a supermarket checkout. Non-preemptive.

⚠️ Convoy Effect

If a long process arrives first, all short processes get stuck waiting behind it. Like a slow truck on a narrow road. This is the main weakness of FCFS — it's not optimal for average waiting time.

SJF — Shortest Job First

Algorithm

SJF: Among all ready processes, pick the one with the shortest next CPU burst. Ties broken by FCFS. Non-preemptive (once started, runs to completion). Proven optimal — gives minimum average waiting time.

The Problem: Predicting Burst Length

We can't know the exact length of the next CPU burst in advance. We estimate it using exponential averaging of past bursts:

τ(n+1) = α × t(n) + (1 − α) × τ(n)

where: t(n) = actual length of nth CPU burst
τ(n) = predicted value for nth burst
α = smoothing factor (0 ≤ α ≤ 1)

Common choice: α = 0.5 (equal weight to past and recent).

  • If α = 0: recent history ignored, τ(n+1) = τ(n) (old prediction unchanged)
  • If α = 1: only last actual burst counts, τ(n+1) = t(n)
⚡ Exam Point

SJF is provably optimal for minimizing average waiting time. However, it can cause starvation — a long process might wait forever if short processes keep arriving. The solution is aging (gradually increase priority of waiting processes).

SRTF — Shortest Remaining Time First (Preemptive SJF)

Algorithm

SRTF (Shortest Remaining Time First) is the preemptive version of SJF. Whenever a new process arrives in the ready queue, the scheduler compares its burst time with the remaining time of the currently running process. If the new process is shorter, it preempts (kicks out) the current one!

⚡ Exam Point — SRTF Formula

The book gives this formula for SRTF waiting time:
Average WT = [(Finish−Arrival−Burst) for each process, summed] / N
From example: [(17−0−8) + (5−1−4) + (26−2−9) + (10−3−5)] / 4 = [9+0+15+2]/4 = 6.5

Common Mistakes to Avoid

MistakeCorrect Understanding
Confusing process and programProgram = passive file on disk. Process = program in execution (active).
Thinking fork() creates a threadfork() creates a new PROCESS (separate memory space), not a thread.
Forgetting to close pipe endsAlways close the unused end of a pipe in each process, or you get hangs.
Wrong FCFS calculation when all arrive at t=0P2 waits = P1's burst time. P3 waits = P1+P2 burst times. Etc.
Confusing SRTF with SJFSJF never preempts. SRTF can preempt a running process when a shorter one arrives.
Turnaround vs Waiting timeTurnaround = total time from arrival to finish. Waiting = time just waiting in queue (Turnaround minus actual burst).
Shared memory vs message passingShared memory is faster (no kernel after setup). Message passing is safer (kernel manages sync).

30-Second Quick Summary — Everything You Must Know

📋 Chapter 1 One-Liners

OS = intermediary between user and hardware.
Kernel = program always running. Mode bit: 0=kernel, 1=user.
Interrupt = hardware/software signal to CPU. Trap = software interrupt.
Storage hierarchy: registers→cache→RAM→SSD→HDD (faster→slower, smaller→bigger).
DMA = block transfer without CPU per-byte involvement.
SMP = all CPUs equal. AMP = one boss CPU. Multicore = multiple cores on one chip.
Multiprogramming = multiple jobs in memory (maximize CPU). Multitasking = rapid switching for interaction.

📋 Chapter 2 One-Liners

System call = formal way for user program to request OS service.
3 parameter passing methods: registers, memory block/table, stack.
6 system call types: process, file, device, info, communication, protection.
OS structures: Monolithic (all-in-one), Layered (onion), Microkernel (minimal kernel), Modules (loadable), Hybrid (combination).
Boot sequence: BIOS → bootloader (GRUB) → kernel → daemons → ready.

📋 Chapter 3 One-Liners

Process memory: text→data→heap↑ gap ↓stack.
5 states: New→Ready→Running→Waiting→Terminated.
PCB = all info about a process (state, PID, PC, registers, memory limits, open files).
fork() returns: child_PID to parent, 0 to child, -1 on error.
execlp() replaces process memory — does NOT return on success.
Zombie = finished child, parent hasn't called wait(). Orphan = parent died first.
IPC: Shared Memory (fast, needs sync) vs Message Passing (slower, sync built-in).
Ordinary pipe: unidirectional, needs parent-child. Named pipe (FIFO): no relationship needed, persists on disk.

📋 Chapter 5 One-Liners

FCFS: non-preemptive, simple, convoy effect, NOT optimal.
SJF: non-preemptive, optimal average WT (same arrival), starvation possible.
SRTF: preemptive SJF, even more optimal with varied arrivals, more context switches.
WT formula: Completion − Arrival − Burst. TT formula: Completion − Arrival.
Preemptive = OS can take CPU away. Non-preemptive = process keeps CPU until done/waiting.
